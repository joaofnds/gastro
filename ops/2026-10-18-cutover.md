# Production cutover, 2026-10-18

The API at https://gastro.fly.dev now uses SQLite on one Amsterdam Machine.
The old Postgres app has been deleted at the owner's request; its verified
cutover archive remains in Tigris. Backup alerts are disabled at the owner's
request; `SQLITE_DEPLOY_READY` remains unset.

## Observed behavior

The first off-host backup completed before API activation. The final image's
protected `recover` command restored Tigris data into an empty directory on the
Amsterdam volume and passed integrity and schema checks. The restored data matched
all four source hashes.

Public authenticated requests read existing migrated data. A separate synthetic
identity created a habit, activity, group and group link. A fresh Tigris restore
contained those writes. Restarting the actual API Machine retained the exact HTTP
response. The synthetic records were then deleted; another remote restore matched
the original source counts and hashes above.

Both Fly health checks passed. `/health` returned HTTP 200 with the database up,
including after Postgres was stopped. Unauthenticated habit access returned 401.
The combined observed API and Litestream RSS was about 79 MiB during these short
checks, with about 126 MiB available to the guest. This is a smoke observation,
not a sustained-load capacity result.

The HTTPS checks from the operator's workstation took approximately 104–193 ms,
including new client connections. The old API host was unreachable, so these
numbers do not establish a deployed before/after speedup. Database operations now
use the local SQLite file and have no API-to-database network hop.

## Postgres retirement and operating limits

After migration, the owner authorized immediate deletion of `gastro-db`,
superseding the initial one-week source-retention plan. The app, its stopped
Machine `9185eeef15d783` and its 1 GB volume `vol_r1owopmonqymdz34` were retired.
A fresh off-host SQLite recovery passed integrity and schema checks before that
deletion. The API continued passing health checks afterward, and Fly lists one
API Machine in Amsterdam with `primary_region=ams`.

The verified Postgres archive remains in Tigris and describes the cutover point;
restoring it alone would omit subsequent SQLite writes. Use current Tigris
recovery or the verified return-transfer procedure in the
[operations guide](README.md). The unrelated `dbtb-bot` app was not changed.

Alerts were skipped explicitly. Litestream continues asynchronous replication,
but a future replication failure will not send a backup alert. The one-second
sync interval does not bound write loss. Automated deployment remains gated.
Account login and missed-ping delivery were not commissioned.

The restore checks used empty directories on the production volume, not a
replacement-host drill. Host-loss recovery time and sustained peak memory remain
unmeasured. The [operations guide](README.md) retains those commissioning checks.

At the current [Fly rates](https://docs.fly.io/about/pricing), the Amsterdam
shared-CPU/256 MiB Machine and 1 GB volume are estimated at about $2.43 per
30 days. Backup requests, traffic and snapshots are additional usage; this is an
estimate rather than an invoice.
